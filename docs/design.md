# 设计说明

## 1. 总体结构

引擎由四层组成，依赖方向自上而下：

```
Engine（编排：计划执行、租约竞争、心跳、恢复、重试、超时）
  ├── Plan        升级/回滚计划构造（纯函数）
  ├── Compat      兼容性校验 + expand/contract 阶段生成（纯函数）
  ├── LeaseManager 获取/续租/接管/释放迁移执行权（fencing）
  └── Store       嵌入式模拟数据库 + 迁移元数据 + 步骤日志（原子持久化）
```

- **Store** 用单个 JSON 文件 `schema_state.json` 保存当前模式、已应用版本列表、
  未完成步骤日志以及租约 token 高水位；租约单独放在 `migration_lease.json`。
- 所有写文件都走“写临时文件 → fsync → `rename`”的原子替换，因此任何时刻磁盘上
  要么是旧状态、要么是完整的新状态，不存在半截 JSON。
- 同一进程内用目录级互斥（`dirMutex`）串行化“读-改-写”，跨进程再叠加目录 `flock`。

## 2. 版本与执行顺序

- 版本按语义化版本比较（主.次.补丁 + 预发布后缀），`"latest"` 表示最高已注册版本。
- 升级（`PlanUp`）：取 `(当前, 目标]` 区间内、**未应用**的版本，按升序执行；已应用版本永不重复。
- 回滚（`PlanDown`）：以**应用顺序为权威**，取需要撤销的后缀，严格逆序执行；
  目标版本保持已应用；缺少回滚定义立即报错（不能安全猜测）。

## 3. 租约、互斥与崩溃接管

`migration_lease.json` 记录 `{owner, fence_token, acquired_at, expires_at}`：

- **获取**：无租约或租约已过期时可获取；否则返回 `ErrLeaseHeld`。
- **心跳续租**：持有者每隔 `HeartbeatInterval` 调用 `Renew` 延长 `expires_at`。
- **崩溃接管**：持有者进程死亡 → 心跳停止 → 租约到期 → 等待者的下一次 `Acquire`
  自动接管，不需要人工干预，也不会永久阻塞。
- **Fencing token（防“假死”复活）**：每次发放租约都让单调递增的 `fence_token` +1
  （高水位持久化在状态文件中，释放后也不回退）。旧持有者若只是长时间 STW/卡顿而未真正死亡，
  它的续租会因 owner/token 不匹配收到 `ErrLeaseLost`，从而立即停手，避免双写。
- **未抢到者的行为**：`Wait` 周期轮询，发现租约释放且版本已推进则收敛返回，
  发现租约过期则接管执行；`Skip` 立即返回 `StatusSkipped`。

## 4. 可恢复执行（核心一致性模型）

一个版本是一个“步骤”，包含若干有序变更。状态文件中持久化 `StepJournal`：

```json
{ "version": "1.0.0", "direction": "up", "applied": [0, 1], "total": 3 }
```

关键不变式：**每个变更与其在日志中的下标记录是一次原子提交**
（`ApplyChangeAndJournalCtx` 在同一个“读-改-写 + rename”事务内完成）。

因此崩溃只会落在两种位置之一：

1. **提交前崩溃**：变更和日志都不存在 → 重跑时该变更重新执行；
2. **提交后崩溃**：变更和日志下标同时存在 → 重跑时跳过该下标，绝不重复应用。

步骤的所有变更提交完成后，`CompleteStep` 在同一个原子操作里“登记/移除版本 + 清除日志”，
所以“版本是否已应用”与“模式是否改完”永远一致，不会出现无法判断的中间态。

恢复流程（`recoverPending`）：引擎成为租约持有者后、执行新计划前，先读取日志；
若存在未完成步骤，无论它是否属于本次计划（例如升级中断后改调回滚），都先按日志续跑该步骤，
然后再继续计划；`Result.Recovered` 会标记本次发生了恢复。

失败语义：单个变更在耗尽重试后返回错误，**保留日志**，状态停留在“已提交前缀”，
租约立即释放（或等待接管）。下次运行即可从该前缀继续。

## 5. 重试与超时

- 每个变更可配置指数退避重试（`RetryPolicy`）。重试只发生在“提交确认之前”，
  因原子记账保证未确认的变更可安全重试。
- `OperationTimeout` 作用于变更的实际提交；`context` 取消/超时会在修改前被检查。
- 每个变更尝试前都会检查心跳通道，一旦续租失败（执行权可能已被接管）立即终止，避免双写。

## 6. 兼容性校验与分阶段路径

滚动发布期间旧版本实例仍在运行，因此 `CheckCompatibility` 对升级计划逐个变更判定：

- 删列 / 重命名列 / 改类型 / 无默认值加非空 / 删表 → 不兼容，直接执行返回 `RejectedPlanError`，
  其中每个 `Violation.Reason` 都可被程序化区分（见 README 表格）。
- 对可分阶段的变更生成确定性阶段（版本号如 `2.0.0+expand`、`2.0.0+cutover`、`2.0.0+contract`）：
  - **expand**：只做向前兼容的新增（影子列、默认值、双写准备），旧实例不受影响，可随应用灰度；
  - **cutover**：回填存量数据并切换读写（通常模式不变，配合应用切流）；
  - **contract**：所有实例升级后，再删除旧结构。
- 删表不存在安全的在线路径，只拒绝、不生成阶段。

分阶段方案的执行流程见 [`safe-rollout.md`](safe-rollout.md)。

## 7. 模拟边界

本项目用嵌入式 JSON 存储模拟真实数据库，目的是验证**编排与一致性逻辑**：

- 模式变更是内存结构变更后整体原子落盘，等价于“DDL 在一个事务里生效”；
- 多“实例”在测试中表现为同一进程内的多个引擎（共享同一数据目录与目录锁），
  跨进程互斥由 `flock` 提供；
- 故障通过 `Engine.SetFaultHook` / `Store.Fault` 注入，可模拟瞬时失败、永久失败、
  执行线程僵死（配合停止心跳模拟崩溃）。
